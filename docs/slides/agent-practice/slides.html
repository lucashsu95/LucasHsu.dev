agent 是什麼？有哪些工具？

agent＝一個迴圈讀專案 → 想 → 真的執行指令、改檔案 → 看結果 → 再想再改，直到它認為完成。
你給任務與完成條件，它執行；它在你的機器上改真的檔案——所以接下來整堂課只有兩個主題：驗證、文件。

終端機 Claude Code

Anthropic 官方；終端機 agent 標竿，教學用它最多

終端機 Codex

OpenAI 官方 CLI（也有雲端版）；GPT 家族、沙箱化

開源 opencode

開源終端機 TUI；接任何家的模型、build／plan 雙模式

開源 pi

極簡輕量、可擴充；API key、訂閱、本地模型都能跑

開源 omo

多模型編排：任務拆給多個模型／子任務協調執行

IDE Antigravity

Google 的 agentic IDE；多 agent 並行、內建瀏覽器

助理型 Hermes

自改進型：經驗沉澱成技能、有持久記憶（MIT）

助理型 OpenClaw

自己機器上的個人助理；經 Discord 等管道操作電腦

第二節 基本操作＋agent 會搞砸 · 23 min

15 分鐘上手：不管你用哪個 agent

  • 開在 practice_pkg/（專案根目錄）啟動 agent。
  • 下指令給有明確完成條件的小任務：「列出專案裡的例外類別」。別丟一句模糊的「幫我看看專案」。
  • 看改動git diff 看實際改動。agent 的總結是 PR 描述，diff 才是真相。
  • 叫它跑讓它跑 verify 腳本，你自己看輸出。exit 0 是唯一可信訊號。
  • 退回改壞就中斷它，用 git 退回。改壞不丟人，不知道改壞了才丟人。

第二節 · agent 會搞砸 01 / 04

規格沒寫死 → agent 靜默挑一種解讀

  1. 觸發下含糊指示：「錯誤的時候回個錯誤訊息就好」→ agent 自信地發明一套錯誤格式（狀態碼、回應體都自己編）。規格空白＝授權 agent 猜。
  2. 怎麼改告訴它真正的契約：「SPEC 寫 409＋Result 外殼，照這個改」→ 用 git diff 看它改對沒有。
  3. 怎麼防SPEC.md 的錯誤回應契約：狀態碼＋回應體格式寫死。寫進文件，agent 就不用每次都猜。
  4. 怎麼驗錯誤 case（負例）寫進 verify：斷言狀態碼＋回應體，重跑看 exit code。

02
第二節 · agent 會搞砸 02 / 04

說完成了，其實是錯的

  1. 觸發agent 回報「實作完成、跑過、全綠」→ 你自己重跑 verify：有一支 case 紅，或 DB 狀態不是該有的值。
  2. 怎麼改指著失敗的 case 叫它修，重跑直到過；改太多就用 git 退回、重下指令。
  3. 怎麼防完成標準不是「它說完成」，是「verify 過」——唯一可信的完成訊號：你的 verify 腳本 exit 0。
  4. 怎麼驗verify 要可重跑＋exit code＋負例，三缺一就不叫 eval；要能從乾淨環境重跑。

第二節 · agent 會搞砸 03 / 04

併發裸 UPDATE

  1. 觸發SPEC 故意不寫併發；當場跑併發 case → 數量扣成負數、同一件被借兩次。
  2. 怎麼改叫它重讀你指定的 TBD-1 機制，重寫；重跑併發 case 到恰好 1 筆成功。
  3. 怎麼防TBD-1 指定機制：唯一約束／樂觀鎖／悲觀鎖／其他，擇一，寫進 SPEC。
  4. 怎麼驗併發 case 寫進 verify/ 必跑：同時借出同一器材，斷言恰好 1 筆成功、qty ≥ 0。不跑併發測試，你根本看不見這個 bug。

第二節 · agent 會搞砸 04 / 04

改了程式，沒改文件

  1. 觸發agent 改完行為，問它「文件更新了嗎？」→ 沒。AGENTS.md／SPEC 還是舊規格。

帶著填 SPEC：要學的是「問法」

如果你是 agent，讀到這份規格會有幾種做法？
你允許幾種？
  1. 第一步業務規則用白話寫：「狀態不是 RESERVED 就不能借出」。先不碰程式。
  2. 第二步枚舉解讀：如果你是 agent，這句話你有幾種做法？會錯在哪？

第六節 收束 ・參考頁

機器人問答 /chat：怎麼串 BIRC-LLM

BIRC-LLM＝中心提供的 OpenAI 相容端點

  • 三個參數：VLLM_BASE_URL／VLLM_API_KEY／VLLM_MODEL＝BIRC-LLM
    URL 與 key 考前提供；key 放環境變數，不寫進程式、不 commit
  • 最快通連：npx @lucashsu95/ai-forge init . --yes
    產生 .env、範例與 AGENTS.md（含三個環境變數的讀法）；再 ai-forge doctor 依序查金鑰→端點→模型
BIRC-LLM · OpenAI 相容 · POST /chat/completions
Authorization: Bearer {VLLM_API_KEY}
{ "model": "BIRC-LLM", "messages": [
　　{ "role": "system", "content": "只用我給的資料回答；查不到就回答：（SPEC 定的固定訊息）" },
　　{ "role": "user", "content": "你查 DB 得到的資料＋會員的問題" } ] }
資料流先查自己系統的真實資料 → 餵 LLM → 回文字。不讓 LLM 憑自己的知識作答。
LLM 掛掉／逾時回你在 SPEC 定的狀態碼＋訊息——不得回 500。
小坑：答案有時在 reasoning_content（content 為空時看它）。
